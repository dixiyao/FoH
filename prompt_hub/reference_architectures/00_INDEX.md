# Reference architectures -- index

This directory is read-only reference material, not instructions and not a template to copy. It exists so you (the server agent, authoring a harness this round) can selectively `read_file` whatever is actually relevant to a decision you are making, instead of having all of it pushed into every prompt. Every pattern below is described as an ADAPTED idea, expressed against or checked against this repo's own primitives (`runtime.generate`, `runtime.call_tool`, `runtime.spawn_agent`/`wait_agent`, `agent_runtime.autonomous.run_autonomous_loop`, `agent_runtime.evolution.evolve_agent`) -- none of it is verbatim source from the systems it draws on, and several of those systems are closed-source or only thinly documented, which the notes below say plainly rather than papering over. Use your own judgment about what actually fits this project; nothing here overrides it.

- **self_evolution_patterns.md** -- concrete patterns for how a harness revises ITSELF round over round: what a self-revision pass should read, how it should decide what changed, how it should write and verify its own next version, and how to keep a self-authored insight library or skill file from becoming a vector for self-inflicted prompt injection. Most directly relevant to your own role, since `agent_runtime.evolution.evolve_agent` already makes your own harness's code the thing that decides its own next version -- this file is about what to put inside that process, not about the outer bookkeeping (which already exists). Includes an adapted pseudocode skeleton against this repo's runtime primitives.

- **planning_and_verification.md** -- externalizing a plan/todo as real workspace state instead of holding it only in one prompt turn, and verifying completed work by actually running it (tests, commands, real output) before finishing rather than trusting your own summary. Draws mainly on first-hand knowledge of Claude Code's and Codex's real architecture, plus one source-verified pattern (omp's plan-mode/model-transition gate, confirmed by reading its actual repository, not a vendor page) and one vendor-documented-only pattern (zcode's Goal-Mode act/verify split, since zcode is closed-source). Includes an adapted PLAN.md-and-run_command skeleton.

- **context_and_memory.md** -- compacting stale history into a durable note instead of relying on truncation alone, and reading a shared insight library/memory selectively by relevance rather than treating every entry as equally worth carrying forward. Draws on hermes-agent's frozen-snapshot memory injection and cache-freshness tradeoff, omp's compress/mental-model summarization, and first-hand knowledge of how long-running coding-agent harnesses manage context. Includes an adapted compaction-and-relevance-filter skeleton.

- **delegation_and_composability.md** -- real division of labor across background sub-agents with an explicit synthesis step (not spawn-and-forget), and plugin/skill-style composability so a harness's own code stays organized as clean, separable units. Draws on deepseek-harness's plugin/seam architecture, zcode's and omp's subagent permissioning and isolation patterns, and first-hand knowledge of Claude Code's sub-agent delegation and modular tool organization. Includes an adapted spawn_agent/wait_agent skeleton and a skill-module registration sketch.

- **external_references_notes.md** -- the honest per-system writeup: what each of omp.sh, zcode, hermes-agent, and deepseek-harness actually is, its license/open-source status, and a plain verdict on how much genuine architectural signal it turned out to hold. Read this if you want to know how much weight to put on a claim elsewhere in this directory, or want the caveats before trusting a pattern attributed to one of these four systems specifically.
